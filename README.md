# AI Resume ↔ Job Description Matcher

An explainable AI-powered web application that compares a PDF resume with a job description, identifies semantic matches and gaps, calculates a deterministic match score, and provides evidence-grounded resume improvement suggestions.

Built as a one-week portfolio MVP with a focus on **explainability, hallucination resistance, privacy, and safe public deployment**.

> **The LLM does not directly invent the final match percentage.**  
> Semantic comparison is performed by AI, while the final score is calculated deterministically in TypeScript.

## Live Demo

**Production:** http://resume-jd-matcher-two.vercel.app/

For a zero-cost demonstration, click **Try Example**.

The example uses a fully fictional precomputed result and does not call the OpenAI API.

---

## What It Does

The application allows a user to:

1. Upload a text-based PDF resume.
2. Paste a job description.
3. Extract structured information from both documents.
4. Semantically compare job requirements with resume evidence.
5. Calculate an explainable match score.
6. Show matched, partial, missing, and uncertain requirements.
7. Provide evidence-grounded resume improvement suggestions.
8. Highlight unsupported requirements without encouraging fabricated claims.

The MVP supports English and German input and can also handle cross-language matching.

---

## Core Design Principle

The project separates **semantic reasoning** from **deterministic scoring**.

```text
PDF Resume
    ↓
Server-side PDF extraction
    ↓
Structured Resume Profile
                         \
                          → Semantic Requirement Matching
                         /
Structured Job Profile
    ↑
Job Description
    ↓
Deterministic TypeScript Scoring
    ↓
Evidence-Grounded Suggestions
    ↓
Final Match Result
```

The AI is responsible for understanding meaning.

Application code is responsible for:

- requirement IDs
- weights
- score calculation
- evidence validation
- suggestion prioritization
- usage limits
- safety constraints

This reduces the amount of product logic delegated to the language model.

## Explainable Matching

The application first converts the Job Description into stable requirements.

Requirements can include:

- skills
- experience
- responsibilities
- education
- language requirements

Each requirement receives a stable ID.

The semantic matching layer may only return:

```text
requirementId
status
explanation
resumeEvidenceIds
```

Supported statuses are:

```text
matched
partial
missing
uncertain
```

The model is not allowed to:

- create new requirements
- invent resume evidence
- assign the final percentage
- reference unknown evidence IDs

Application code validates the result before scoring it.

---

## Deterministic Scoring

The final score is calculated in TypeScript rather than generated by the LLM.

### Requirement Weights

```text
Required      = 2
Preferred     = 1
Unspecified   = 1
```

### Match Values

```text
Matched       = 1.0
Partial       = 0.5
Missing       = 0.0
Uncertain     = 0.0
```

### Formula

```text
earned points
────────────── × 100
possible points
```

The final percentage is rounded by application code.

Category scores are also calculated independently for:

- Skills
- Experience
- Responsibilities
- Education
- Languages

If a category contains no requirements, the UI displays `N/A` rather than inventing a score.

## Resume Integrity and Hallucination Safeguards

A major goal of the project is to avoid generating stronger claims than the resume actually supports.

The structured extraction layer follows strict source separation:

```text
Resume Profile
→ may only use Resume content

Job Profile
→ may only use Job Description content
```

Resume evidence must come from the original resume.

When information is ambiguous, the system prefers:

```text
null
[]
uncertain
```

instead of guessing.

The application must never fabricate:

- skills
- employers
- responsibilities
- achievements
- metrics
- certifications
- proficiency levels
- years of experience
- qualifications

## Evidence-Grounded Resume Suggestions

Suggestions are generated deterministically from the validated Match Result rather than through an additional LLM call.

Current suggestion types include:

```text
increase_visibility
clarify_supported_scope
protected_gap
needs_verification
```

### Matched Requirements

The application may recommend making existing evidence more visible.

### Partial Requirements

The application may suggest clarifying only the scope already supported by the resume.

Partial suggestions include a claim boundary to prevent accidental exaggeration.

### Missing Requirements

The application does **not** suggest pretending that the missing requirement exists.

Instead, it explicitly marks the requirement as unsupported and warns the user not to add it unless it is genuinely true.

### Uncertain Requirements

The application requests verification rather than making assumptions.

## PDF Processing

PDF extraction is performed server-side using `unpdf`.

Current safeguards include:

- PDF MIME / extension validation
- `%PDF-` signature validation
- maximum file size: **4 MB**
- maximum page count: **50**
- maximum extracted text: **100,000 characters**
- empty / damaged / unsupported PDF handling
- password-protected PDF handling
- image-only / scanned resume rejection
- in-memory processing
- resource cleanup

The MVP intentionally does **not** use OCR.

Scanned or image-only resumes receive a helpful error instead.

### Known PDF Limitation

Multi-column resume layouts may not preserve perfect visual reading order during text extraction.

The application therefore instructs the structured analysis layer to prefer uncertainty over assigning information to the wrong education or experience entry.

Layout reconstruction is outside the scope of this MVP.

## Public Deployment and Cost Protection

The public application contains multiple layers of protection against uncontrolled paid API usage.

### Per-Client Limits

```text
PDF extraction
→ 10 requests / hour / client

/api/analyze + /api/match
→ shared 6 paid calls / hour / client
```

A normal complete real analysis uses two paid calls:

```text
/api/analyze
+
/api/match
```

Therefore, one client can normally perform approximately **three complete real analyses per hour**.

### Global Limit

```text
40 paid OpenAI calls / day
```

This provides an additional ceiling if abuse originates from multiple clients.

### Distributed Rate Limiting

Rate limiting uses:

- Upstash Redis
- `@upstash/redis`
- `@upstash/ratelimit`

An in-memory `Map` is intentionally not used for production protection because independent serverless instances do not share reliable process memory.

---

## Client Privacy in Rate Limiting

Raw client IP addresses are not stored in Redis.

The application creates a pseudonymous identifier using:

```text
HMAC-SHA-256(client address, secret salt)
```

Upstash stores only the resulting hash and expiring limiter counters.

Rate-limit namespaces are separated by deployment environment:

```text
development
preview
production
```

Environment resolution uses Vercel deployment metadata rather than `NODE_ENV`.

If the deployment environment cannot be safely determined on Vercel, rate limiting fails closed.

---

## Fail-Closed Behavior

Paid AI work is intentionally fail-closed.

If Upstash is unavailable or rate-limit configuration cannot be verified:

```text
Request
   ↓
Rate limiter unavailable
   ↓
HTTP 503
   ↓
OpenAI is NOT called
```

If a user exceeds the allowed quota:

```text
HTTP 429 Too Many Requests
```

The public **Try Example** remains available even when real analysis is unavailable.

---

## OpenAI Cost Controls

The application uses multiple layers of cost protection:

```text
Frontend duplicate-request protection
            ↓
Input and complexity limits
            ↓
Distributed per-client rate limiting
            ↓
Global daily paid-call ceiling
            ↓
OpenAI SDK retry disabled
            ↓
Provider-side project spend limit
```

OpenAI clients are configured with:

```text
maxRetries: 0
timeout: 60 seconds
max_output_tokens: 12,000
store: false
```

Disabling SDK retries ensures that one accepted limiter operation produces at most one automatic OpenAI SDK attempt.

The public deployment also uses a dedicated OpenAI project with a deliberately low enforced spending limit.

## Privacy

Uploaded resumes are:

- processed for the active request
- parsed in memory
- not written to application disk
- not stored in a resume database
- not retained by this application as resume history

Resume content and the Job Description are sent to OpenAI when the user requests real AI analysis.

OpenAI requests use:

```text
store: false
```

This application does not claim that an external AI provider performs zero temporary processing or abuse-monitoring retention.

Users should avoid uploading information they do not want processed by an external AI service.

Development-only technical details are hidden in production.

API responses containing user-derived information use:

```text
Cache-Control: no-store
```

## Known Limitations

This project is intentionally a focused portfolio MVP.

Current limitations include:

- text-based PDFs only
- no OCR
- multi-column extraction order may be imperfect
- no user accounts
- no persistent history
- no resume database
- no automatic resume rewriting
- no guarantee that Job Descriptions are complete or internally consistent
- semantic AI output may still contain errors
- rate limiting is designed for a public portfolio demo, not enterprise-scale abuse prevention

The result should be treated as an assistive comparison tool, not an automated hiring decision.

## Why This Project Uses Both AI and Deterministic Logic

A simpler implementation could ask an LLM:

> "Compare this resume to this job and return a percentage."

This project intentionally does not do that.

Instead:

```text
LLM
→ understands semantic relationships

TypeScript
→ validates structure
→ enforces evidence references
→ calculates scores
→ prioritizes suggestions
→ enforces safety rules
```

This architecture makes the result more:

- explainable
- testable
- predictable
- auditable
- resistant to hallucinated scoring
